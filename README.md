# CS-320
Software Testing, Automation, and Quality Assurance

I used to think that if my code ran and the result looked right, I had a good reason to believe it worked. Writing the contact service tests made me question that because I could create a contact with valid information and still have no idea what would happen if someone left a field null or entered a phone number with nine digits. I used JUnit to check those inputs and the methods for adding, deleting and updating contacts. Having those checks helped because I could change the code and run them again instead of trying to remember everything I had checked before. I think making software secure takes more work than that because someone could enter valid information and still be trying to view or change records that don’t belong to them. My contact service didn’t include user accounts or access controls. If I developed it into a complete app, I would need to decide who should have access to each record and test that the app enforces those rules.

The requirements gave me a way to connect what the user needed with something I could check in the program. For example, the contact ID couldn’t change after I created the contact but the name, phone number and address could. That meant I had to think about those fields differently instead of treating them all as information someone could edit. I can see myself using that same approach with a customer by asking what they need to do and working through an example with them before I start writing code. If they asked for a way to update a contact, I would want to know which information they meant and what should happen if the new value was invalid. I think those questions would save me from building something that makes sense to me but doesn’t work the way they need it to.

Breaking the project into a contact object and a service helped me understand how I could design a program without putting all the work in one place. I knew the Contact class checked the field values and ContactService handled the stored records, so when I needed to change something I had a place to start looking. I’m still learning how to make those decisions on my own but I could see the benefit when I tested each class and then checked the service working with the contacts. In future projects, I would start by writing down what the program needs to do and use that to decide which parts I need. I could then build and test those parts as I go. I think having a structure I understand would help me later because I wouldn’t want every new feature to mean sorting through the whole program just to find where it belongs.
